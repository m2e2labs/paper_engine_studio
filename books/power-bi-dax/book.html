DAX Is Not Excel, and Not Power Query

Two languages in one app, and Excel isn't either of them.

Let's say you've typed a formula that would've worked in Excel, and Power BI has underlined it in red. You're writing in the wrong language.

Power Query's language is M. It runs on the way in, while the data loads. DAX runs later, when a chart asks it something. And DAX never points at a cell. It takes a whole column, or a whole table.

M shapes the data on the way in. DAX answers questions once it's there.

DO THIS NOW

Open Power Query, read the Applied Steps list, then close it again. Every step in that list is M. None of it is DAX.

Measure, Calculated Column, Calculated Table

Same language, different homes. The wrong one costs you speed.

Let's say you right-clicked a table and were offered New measure, New column and New table.

Every one of them is DAX. A calculated column works a value out for every row and keeps it, taking up room even when nobody looks. A measure keeps nothing until something asks.

A column is something you store. A measure is something you ask.

Right-click a table in the Data pane and read the New options without clicking. Say which one you want, and why, before you pick.

Two ways in, one bar, and a list that finishes your typing.

When the Formula Turns Red

Usually one problem, and a habit that fixes it for good.

Let's say there's a red line under your formula and the message beneath it means nothing to you yet. Usually Power BI can't tell which column you mean.

So write a column as the table name and then the column in brackets, every time. Write a measure with no table name: it can move tables later, and a formula that never named one keeps working. And a blank isn't an error.

A column always says which table. A measure never does.

Filter Context: The Question the Cell Is Asking

One formula, a different question in every cell.

Let's say one measure sits in a table and every row shows a different number. Nothing is broken.

A separate query runs for every cell. The formula is the same each time; the filters around it are not. Change a field or a slicer and you have changed the question.

One formula, asked again in every cell, with different filters each time.

DO THIS NOW

Put the same measure in a card and in a table split by category. One formula, two numbers.

Row Context: What a Calculated Column Sees

One row at a time, and why a total looks broken.

Let's say you added a calculated column that sums an amount, and every row came back with the same number. It looks broken. It isn't.

A calculated column is worked out one row at a time, and sees every column of that row. But a sum doesn't want a row. It wants the whole column, so it gets the whole table, every time.

A row context says which row you're on. It doesn't narrow what a total sees.

DO THIS NOW

Add a calculated column of = SUM over your amount column. Same number, every row.

CALCULATE: Changing the Question

The one function that can change the filters a measure sees.

Let's say you need sales for one colour, and the visual isn't filtered that way. CALCULATE works your expression out in a filter context it changed first.

Name a column nothing had filtered and your filter is added. Name one the visual already filtered and yours replaces theirs. That is where the surprises come from.

CALCULATE doesn't do the sum. It changes what the sum is looking at.

DO THIS NOW

Split a table by Colour, with your total in it. Add the total again, wrapped in CALCULATE with Colour = "Blue". That column stops moving.

Context Transition: The Thing Nobody Explains

Inside a row, a measure quietly starts seeing only that row.

Let's say you dropped a measure inside an iterator and the answer came out nothing like the same maths written longhand.

That is context transition. Put CALCULATE inside a row context and the row you are on becomes a filter. You needn't type it either: a model measure does it on its own. It is why a measure behaves differently inside an iterator.

Inside a row, a measure stops seeing the table and starts seeing the row.

SUM, AVERAGE, MIN and MAX

One column in, one number out, every time.

Let's say you need the total of an amount column. That is an aggregator's whole job: one column in, one number out.

SUM adds the numbers up. AVERAGE, MIN and MAX are written the same way over the same column, so learning the shape once gets you the rest of them. MAX will also take two expressions and hand back the larger of them.

One column in, one number out. That is the whole shape.

Counting Things Without Getting It Wrong

They all count. They don't agree on real data.

Let's say two people counted your customers and got different numbers. Nothing errored. They just picked different count functions.

COUNT skips blanks and won't take true or false. COUNTA counts the same rows but does. COUNTROWS just counts rows, and Microsoft recommends it when rows are the point.

If the counts disagree, that is your data talking, not a bug.

DO THIS NOW

Put all of them over the same table. If they don't match, you've learned something about your data.

DIVIDE, and the One Time the Slash Is Fine

A slash can leave Infinity in the cell. DIVIDE leaves a blank.

Let's say a product has sales this month but its quantity came in blank. The slash shows Infinity in the cell, and it ships.

DIVIDE hands back a blank instead, and it takes a last argument for what to show in place of it. Blank is usually what you want, because a visual drops the groups that come back blank and shows only the ones with data.

Where the bottom could be zero or blank, use DIVIDE. Where it is a constant, the slash is fine.

DO THIS NOW

Find a measure of yours with a slash in it. If the bottom isn't a constant, rewrite it with DIVIDE.

IF and SWITCH

Nest a few IFs and nobody can read it, including you.

Let's say you are banding each sale into small, medium and large. With IF you nest one inside another inside another, and the formula stops being readable fast.

SWITCH lays the same choices out flat, one condition and one result to a line. Start it with TRUE and it handles ranges and bands. The first condition that matches wins, so the order you write them in matters, and every result has to be the same data type.

Once you are nesting IFs, Microsoft's own advice is to reach for SWITCH.

What an Iterator Actually Does

Row by row first, then add it all up.

Let's say the maths has to happen on each row before anything gets added together. That is the whole reason an X function exists.

An iterator takes a table and an expression, works the expression out once on every row of it, and then aggregates all of those answers. Every X function is that same shape. It's there so you decide how the calculation summarises, instead of taking what a plain aggregation gives you.

For each row, do this, then add it all up. That is an iterator.

DO THIS NOW

Read a measure out loud as: for each row, do this, then add it up. If that fits, you want an X function.

Absolute Beginners · No. 17

SUMX vs SUM: When You Need the X

Add a column, or build the value first and then add.

Let's say you need revenue, and your table holds quantity and price but not the two multiplied together. Summing quantity and multiplying by an average price gives a number that looks plausible and is wrong.

SUM adds numbers that are already sitting in a column. SUMX builds the value on each row first, then adds those up. Reach for the X whenever the values need working out or filtering before they can be summed.

If the column isn't there yet, you need the X.

DO THIS NOW

Work revenue out both ways in one table: SUM of Qty times AVERAGE of Price, and SUMX. Note which one you'd have shipped.

Iterators page: AVERAGEX works out the arithmetic mean of a set of expressions evaluated over a table, every X function takes a table as its first argument and an expression as its second, MAXX returns the largest number found by evaluating the expression for each row, and MINX returns the smallest.

Absolute Beginners · No. 18
Iterators

AVERAGEX, MAXX and the Rest of the Family

SUM, AVERAGE, MIN and MAX each have an X twin.

Let's say you want the average sale per customer, not the average of the rows. Different questions, and usually the first one was meant.

AVERAGEX over the Customer table, with a sales measure as the expression, answers it. The X functions all share one shape: a table first, an expression second. MAXX gives the largest it produced, MINX the smallest.

Table first, expression second. Learn it once, use it everywhere.

DO THIS NOW

Write AVERAGEX over your Customer table with a sales measure. That's average per customer, properly.

RELATED: Reaching Across a Relationship

The value lives in the other table. Go and get it.

Let's say your Sales table has a product key in it but the category is over in the Product table. RELATED goes and fetches it.

It follows a relationship that already exists, from the many side to the one side, and it only works where there's a row context. It can't invent a connection: no relationship, no RELATED. RELATEDTABLE goes the other way and hands back rows.

If RELATED errors in a calculated column, check the relationship.

DO THIS NOW

In a calculated column on Sales, write = RELATED(Product[Category]). If it errors, fix the relationship.

FILTER Returns a Table, Not a Yes or No

A smaller table comes out, not a true or false.

Let's say you wrote a measure that was just FILTER, and Power BI wouldn't have it. FILTER doesn't answer yes or no. It hands back a table.

So it always sits inside something that wants a table. It is also slower than a plain condition, so pass a plain true-or-false filter where you can and keep FILTER for when you can't.

A measure can't go in a plain filter. That is when FILTER earns its place.

ALL: Taking a Filter Off on Purpose

The visual stays filtered. Your measure doesn't have to.

Let's say every row of your table shows its own total, and you need the total of everything beside it to divide by. ALL is how you get it.

ALL ignores the filters on a column or on a whole table, so the measure sees the bigger picture while the visual around it stays sliced. Name columns instead of the table and only those filters come off, with the rest still applying.

Where your tool has REMOVEFILTERS, Microsoft says use that for this job instead.

Percent of Total, the Pattern You'll Reuse Forever

This row's value, over the same value unfiltered.

Let's say you want each category's share of the whole. That's this row's value over the same value, unfiltered.

The top keeps whatever the row is filtered by. The bottom strips the filter off, using ALL. Microsoft's own example is this exact shape: a sum over the same sum, filters removed.

Once this clicks, a great many patterns in a real report turn out to be variations on it.

SELECTEDVALUE: Reading the Slicer

One thing picked, or a fallback. Never stale.

Let's say your chart title says Sales by Month whatever the reader picks. It goes stale the moment they click.

VALUES gives the distinct values. SELECTEDVALUE gives the one picked.

Why Every Model Needs a Date Table

No date table, no time intelligence. Not really.

Let's say last year came back blank and nothing errored. That is the shape of a missing date table, and a blank ships where an error wouldn't.

The time functions need a table that is nothing but dates: one row per date, no blanks, no missing days, whole years. Mark it and Power BI checks for blanks, duplicates and gaps, and drops the hidden tables it had been making for you.

A gap between the first date and the last throws an error. Better than silence.
